## 1. 执行摘要

项目已经具备完整产品站和 CMS 雏形，但“实现扩张速度”明显快于“PRD 和表达系统沉淀速度”。现在最需要处理的是三类债务：

| 类别 | 结论 | 优先级 |
|---|---|---|
| 文档债 | Master PRD 与当前代码不一致；产品页数量、路由状态、技术栈说明存在过期内容 | P0 |
| 表达债 | 多数页面能展示内容，但未形成统一的车主决策路径；车型页容易变成项目堆叠 | P0 |
| 视觉债 | 深色系统一致，但部分 Hero、缺图状态、长列表、后台表格仍有半成品感 | P1 |
| 工程债 | 数据层有 `any` 豁免；README/ARCHITECTURE 与 AGENTS 对 OSS、Radix、路由数量描述不一致 | P1 |
| 验证债 | 已有全站测试 PRD，但还需要把 390/768/1440 浏览器检查固定到每次 UI 改版流程 | P1 |

### 2.1 技术栈一致性问题

| 问题 | 影响 | 建议 |
|---|---|---|
| README 仍写 “shadcn/ui + Radix” 和 “OSS 上传” | 新接手者会按错误技术路线实现 | 以 `AGENTS.md` 为准，README/ARCHITECTURE 后续同步 |
| `docs/ARCHITECTURE.md` 路由数量明显过期 | 审计和规划引用会失真 | 后续把架构文档改成“当前统计 + 自动脚本来源” |
| `src/lib/data.ts` 使用多处 `any` 豁免 | 与“TS strict 禁 any”冲突 | 用 API response schema 或局部 typed DTO 替代 |
| `StoreForm.tsx` 对 zodResolver 使用 `as any` | 表单类型安全弱 | 单独做表单类型修正，不混入视觉改版 |

## 3. 信息架构审计

### 3.1 当前结构

公开站已经形成 7 个页面族：

- 首页：`/`
- 品牌：`/brand` `/brand/certifications` `/brand/history`
- 产品中心：`/product`
- 服务线：`/product/ppf` `/window-film` `/color-film` `/electric-steps` `/wheels` `/chassis` `/flooring` 等
- 品牌/车型专题：`/product/<brand>`、`/product/<brand>/<model>`
- 门店网络：`/agent`、省市页、门店详情
- 资讯与联系：`/news`、`/contact`

后台形成 5 个页面族：

- 登录、Dashboard、数据分析、文章、门店。

### 3.2 主要问题

| 问题 | 表现 | 后果 |
|---|---|---|
| 入口过多但决策路径不稳定 | 产品中心既有车型、服务、组合、整理中品牌 | 用户容易不知道该先点车型还是项目 |
| 车型页和服务页边界不清 | 车型页大量项目，服务页讲项目价值 | 内容会重复，SEO 和用户阅读都分散 |
| “整理中”内容外露较多 | `planned`、`pending-review`、`missing` 状态大量存在 | 品牌官网感下降 |
| 文档没有总分层 | Master、public-site、product PRD 互相重复 | 实现者难判断哪个文档是准绳 |

### 3.3 建议 IA

```text
首页
├─ 认识蓝辉: 品牌可信 + 门店可信
├─ 找方案
│  ├─ 按车型找: 品牌页 → 车型页
│  └─ 按项目找: 服务线页
├─ 看案例/内容: 资讯
└─ 咨询到店: 微信 + 门店详情 + 联系页
```

## 4. 页面表达审计

### 4.1 首页 `/`

优点：

- H1 使用品牌名，CTA 清晰，结构简单。
- 已经有品牌能力、核心服务、产品入口的基本漏斗。

问题：

- Hero 背景主要是渐变和光斑，缺少真实门店/施工/产品视觉资产，容易显得模板化。
- “800 亩制造厂区”等强背书没有在页面内形成证据链。
- 产品入口仍偏“内部服务分类”，对刚提车用户的“我该先做什么”回答不足。

建议：

- 首屏加入真实产品/施工/门店视觉资产。
- 首页产品入口改成“新车保护、隔热隐私、外观风格、上下车便利、底盘防护、车型方案”这类用户语言。

### 4.2 产品中心 `/product`

优点：

- 已经实现“按车型找 / 按项目看 / 推荐组合”方向。
- `src/lib/product-routes.ts` 已成为较好的 source of truth。
- 移动端有 tab 分段，能缓解长页面。

问题：

- 桌面端信息量大，Hero、品牌矩阵、材质切片、服务地图、整理中区域全部堆叠，首屏判断成本偏高。
- `plannedCount={ALL_SERVICES.length}` 文案表达容易误导，它不是计划品牌数量。
- 整理中品牌区域包含大量 TopicBanner，视觉上像内容已上线，但状态未必稳定。

建议：

- 把 `/product` 定义为“导购分流页”，而不是“所有内容展示页”。
- 桌面端三块主入口固定：按车型、按项目、推荐组合；整理中内容默认收敛。

### 4.3 品牌/车型专题

优点：

- 已形成 topic-page pattern：数据模块 + 组件目录 + 页面 + JSON-LD。
- 多品牌覆盖全面，利于 SEO 入口扩展。

问题：

- `pending-review` 和 `missing` 状态较多，视觉上仍会出现“半成品”感。
- 品牌页之间骨架相似，品牌差异主要靠主题色和标题，不够有辨识度。
- 车型页项目多时，移动端滚动很长，用户难以快速找到高优先级项目。

建议：

- 所有缺图状态必须有明确文案、图标、边框和可访问 alt，不允许空白容器。
- 车型页首屏统一给出“本车型优先做什么”的 3 项摘要。
- 项目卡按“新车必做 / 舒适升级 / 外观升级 / 小配件”分组，不直接平铺全部。

### 4.4 门店与联系

优点：

- 有静态 fallback，build 不依赖 DB。
- 门店详情可作为转化末端。

问题：

- 历史审计记录过测试门店污染风险。
- 联系页 PRD 中仍提到假 400 和占位信息风险，需要继续禁止。

建议：

- 门店公开数据必须建立“真实可展示”状态门槛。
- 联系页只展示真实电话、真实微信或明确“到店咨询”路径。

### 4.5 Admin

优点：

- Dashboard 已拆分为欢迎、待办、KPI、门店网络、内容健康、趋势、最近操作、快捷入口。
- `(dashboard)/layout.tsx` 有 `auth()` 守卫。

问题：

- 后台布局在移动端仍需要单独验证，表格页和图表页是主要风险。
- admin 视觉表达相对工具化是正确方向，但需要完善错误态、空态和确认态。

建议：

- 后台不追求营销视觉，优先可扫读、可批量操作、错误反馈明确。
- 表格页面移动端应有卡片化摘要或横滚提示。

## 5. 响应式审计

| 视口 | 当前风险 | PRD 约束 |
|---|---|---|
| 390px mobile | 产品/车型长页滚动过长；表格横滚；缺图容器占空间 | 必须有分段、折叠、锚点或 tab；无横向滚动 |
| 768px tablet | 产品矩阵和后台布局容易处于尴尬中间态 | 需要单独截图验收，不允许只测 mobile/desktop |
| 1440px desktop | 信息量过大时会变成“组件陈列” | 首屏必须明确下一步，页面区块要有主次关系 |

## 8. 结论

蓝辉官网当前的核心价值已经从“做出页面”转向“把页面组织成可信的购前咨询系统”。下一阶段不应继续无约束新增页面，而应先统一：

1. Master PRD 的当前事实。
2. 页面级表达和验收标准。
3. 产品中心、车型页、服务线页的边界。
4. 缺图、整理中、计划中内容的展示规则。
